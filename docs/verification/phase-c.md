## Lifecycle, concurrency and recovery

`fileLifecycle.test.ts` uses real authenticated PATCH/DELETE requests, independent pinned PostgreSQL clients and explicit barriers. Both keep-first values (enable and disable persistence) commit against an actually stale expired candidate; cleanup locks, rechecks and skips it, leaving bytes intact. Both expiry and manual claim-first cases block a waiting keep for each persistence value, which receives 409, then remove bytes and finalize only the same claim without altering storage identity or retention. An authenticated manual DELETE holds the first claim while an independently authenticated keep waits; repeated DELETE completes safely. Exact-now and past-expiry requests reject both persistence values with 410 and unchanged SQL/bytes; a waiting operation samples time and API-key/session authority after its lock wait. A genuine signed-cookie case checks database wall time after transaction start.

The expiry tests retain PostgreSQL microseconds. A future `.123456` timestamp at injected `.123` time remains available to private metadata/download and public download and is ineligible for cleanup. This test exposed a real public-share mapping defect: SQL allowed the file but a rounded JavaScript Date rejected it. The public mapping now carries exact timestamp text. Both expired and pending keyset cursors use exact SQL timestamp text as well.

Fairness evidence includes 501 actual synthetic byte files with the first 100 selected by SQL `(expires_at,id)` order and failed by stable storage key. The other 401 use the real unlink helper and have absent bytes/finalized metadata; a second complete sweep retries the same failing prefix without changing claims or releasing its bytes. Separate SQL cursor/budget tests cover 1203 same-microsecond expired rows across the 1000-attempt tick budget and 1200 permanently failing pending claims alongside newly expired work; those larger tests use injected deletion callbacks, not additional real-unlink evidence. Separate progressing cursors and a reserved expiry budget prevent pending failures from monopolizing ticks. A newly arriving expired tail progresses even while the pending sweep remains incomplete. Failed sweeps do not advance the success timestamp.

Injected EACCES, claim COMMIT before/after outcome, verification outage, finalization reply loss, retention reply loss and after-unlink failure tests assert durable claim identity, status, bytes and capacity. A DELETE returns controlled 503 while completion is uncertain. Fresh exact ownership verification is required before unlink or uncertain success; completed retries return 200 while retained metadata exists, then 404 after purge. Recounts replace measured totals, so repeated absent-byte recovery cannot release capacity twice. These are deterministic adapter/fake-clock crash-window simulations over real PostgreSQL/files, not actual process termination or power-loss evidence.

Production startup performs schema/storage/persistent-volume association checks before starting immediate or periodic maintenance. Tests cover failed readiness starting no scheduler, immediate pending recovery, coalescing concurrent runs and stop awaiting an in-flight pass. Routes and maintenance use the same admission and active-upload runtime; failed/unknown uploads stay protected and admission recounts wait for reservations to settle. The existing bounded shutdown deadline remains in effect.

## Reconciliation, retention and identity

Reconciliation tests cover exact grace boundaries, recent post-link files, old active leases, synthetic temp/final hardlinks, metadata ownership, malformed 36-character filenames, database outage, missing/replaced roots and repeat passes. The scanner considers only the two owned directories and canonical opaque names; it does not follow symlinks. A fresh runtime pointed at an unpaired empty root refuses startup/destructive maintenance and preserves the original pending bytes. Persistent database/volume identity supplements process-local device/inode checks.

`maintenance.test.ts` really uploads code A and bytes, creates a share, deletes/finalizes it, advances retention and runs the production purge. File details, shares and events disappear while the code-only registry retains A. Offering A then B allocates B; authenticated A metadata/download stay 404 and never expose B's bytes. The proof repeats after migration/restart and complete synthetic registry export/restore into a fresh migrated database. This fixture export/restore is not the Phase E release backup workflow. A failing purge transaction preserves reservations, and remaining physical bytes prevent detail purge.

The review-fix purge regression creates 501 deleted rows with a retained-byte prefix of 500 and an absent-byte tail, using exact adjacent microsecond timestamps. Repeated 500-attempt pages reach and purge the tail, preserve all reservations and retained bytes, and withhold success until an entire unblocked sweep completes. A second variant includes an invalid directory path within the prefix; individual path failure cannot starve the tail. Transaction failure preserves the cursor for retry and cannot record success.

Expired sessions and old revoked/expired shares are purged while active records remain. Normal, immediately recovered and deferred recovered uploads each attempt one safe creation event. Tests assert one persisted event, idempotent insertion, exact bytes/metadata/capacity and visible health failure under an event-table trigger outage for each path. Event-write failure leaves confirmed upload/deletion successful. Events contain fixed types, IDs and allowlisted details without actor names, credentials or content. Storage status reports measured/reserved bytes and per-job attempt/success/failure state; public endpoints disclose no storage state.

There is no registry purge/reuse setting. Before a stale restore, operators must disable issuance with the validated `FILE_ISSUANCE_ENABLED=false` setting and recover all later code history before re-enabling it. Missing history cannot be inferred from a snapshot. Metadata and event retention each validate 1-3650 days to prevent Date overflow. See [retention and recovery](../retention.md) for volume pairing, missing-byte repair, logs, copies and backup limits.

## Final public-share admission review fix

The final review found that a public download could use a timestamp and file snapshot captured before a PostgreSQL wait. Before changing production code, the new `shareAdmission.test.ts` reproduced HTTP 200 after exact/past share expiry and after a committed file deletion claim, where 410 was required. These three failures used independent pinned backend clients and observed `pg_blocking_pids` barriers, without timing sleeps. Revocation and the concurrent cap already passed that initial six-case run.

Admission now locks file first and share second, checks current eligibility and atomically reserves the count using time sampled after pool/row waits, then runs a fresh route guard immediately before storage opening under those locks. Delayed denial rolls back the count and opens no stream. Exact share and file expiry text preserves PostgreSQL microseconds. A successful count commits before sending bytes; locks do not span delivery. Storage-opening failure rolls quota back. Commit failure closes an opened stream and sends no bytes; a count already committed can remain consumed after a lost reply. The [API contract](../api-contract.md) defines that admission point and its limits.

The final focused run passed 14 cases; the final combined run above includes them all. It covers exact/past expiry, revocation, file expiry and deletion claims during actual lock waits; an exhausted ten-client pool wait; share/file expiry after SQL but before opening; eight concurrent requests capped at two successes; microsecond boundaries; storage-open failure; before/after-COMMIT reply failures; and an admitted stream completing after expiry/revocation while the SQL locks are released. Denials assert zero counts and no storage-open calls; lock races also assert final SQL claim/revocation state and retained real fixture bytes. Stream and commit failures use explicit adapters, not process-kill simulations. Existing suites retain actual filesystem download coverage.

The optional upload accounting/test readability finding was also resolved with formatting only, covered by existing unit and real-PG upload tests. The final source change leaves migrations 001–004, startup and configuration behavior unchanged. Earlier Linux/Compose evidence therefore remains applicable within its stated scope; those checks were not repeated. Controller final review/scans and the Phase C gate passed. ## Limits and remaining acceptance

The supported capacity/maintenance model is one app process with an exclusively owned volume; multi-process writers and adversarial inode swaps are unsupported. Failure health counters and sweep cursors are process-local; durable claims and code reservations persist. Database/disk failures can extend reclamation indefinitely. Event failures require review; there is no guaranteed event replay queue or every-byte download audit.

Windows tests and Linux containers do not establish native Linux host setup, other architectures or every filesystem's durability. Abrupt process termination, power loss, release upgrades/restores, public clone/build/CI/artifact acceptance and browser/agent/phone workflows remain D/E work. Historical Phase A/B evidence remains historical. Release acceptance remains pending.
